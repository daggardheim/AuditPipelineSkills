# Runner Contract

This document defines the execution contract for the orchestrator that launches agent invocations on the runbook pipeline.

It is not the prompt itself. It is the orchestration contract that the wrapper script (audit_loop.py) must follow.

## Purpose

Run the S1-S5 loop without human intervention while keeping each stage isolated in a fresh context window.

## Inputs

- Repository root
- runbooks/index.md
- The current row number or the ability to discover the next eligible row
- The active row's runbook file (for S2-S5) or output path (for S1)
- The allowlisted shared files for the current stage
- The stage-specific prompt for the current agent invocation
- Explicit allowlisted text files, with large external sources left as path manifests

## Agent dispatch

The orchestrator reads `_agent-permissions.yaml` to determine the agent, tools, and file scope per stage. The table below shows a Claude (creator) + Codex (auditor) configuration:

| Stage | Agent | CLI command |
|-------|-------|-------------|
| S1 | Creator (Claude) | claude -p "{prompt}" --output-format json --max-turns 10 --allowedTools Read,Write,Edit,Glob |
| S2 | Auditor (Codex) | codex exec "{prompt}" --sandbox workspace-write |
| S3 | Creator (Claude) | claude -p "{prompt}" --output-format json --max-turns 10 --allowedTools Read,Write,Edit,Glob |
| S4 | Auditor (Codex) | codex exec "{prompt}" --sandbox workspace-write |
| S5 | Auditor (Codex) | codex exec "{prompt}" --sandbox workspace-write |
| S6 | Auditor (Codex) | codex exec "{prompt}" --sandbox workspace-write |
| S7 | Creator (Claude) | claude -p "{prompt}" --output-format json --max-turns 10 --allowedTools Read,Write,Edit,Glob |
| S8 | Auditor (Codex) | codex exec "{prompt}" --sandbox workspace-write |

For a Claude-only setup, replace the Codex commands with:
- S2, S4: claude -p "{prompt}" --output-format json --max-turns 3 --allowedTools Read,Glob
- S5: claude -p "{prompt}" --output-format json --max-turns 3 --allowedTools Read,Write,Edit,Glob
- S6, S8: claude -p "{prompt}" --output-format json --max-turns 3 --allowedTools Read,Glob
- S7: claude -p "{prompt}" --output-format json --max-turns 10 --allowedTools Read,Write,Edit,Glob

## Required behavior

1. Read runbooks/index.md.
2. Find the first eligible row:
   - S1 = todo -> launch creator agent
   - S1 = done, S2 = not-started -> launch auditor agent for S2
   - S3 = todo -> launch creator agent for S3
   - And so on through S5
3. If no row is eligible, stop and wait for the next scheduled tick.
4. For the eligible row, determine the active stage.
5. Launch exactly one agent invocation for that stage.
6. Preload explicit allowlisted text files into the prompt before launch.
7. Keep large external sources path-based or manifest-based instead of inlining raw content.
8. Use a fresh context for every stage invocation.
9. Do not rely on prior chat history for continuity.
10. Wait for the stage to finish.
11. Persist the stage result to the grid and state files.
12. For S5, run the post-run validator before closing the row.
13. If the validator passes, finalize the row, write End and Total, and unlock the next row in index order whose S1 is `not-started`.
14. If the validator fails, mark the row blocked and stop that row.
15. Repeat until the row reaches S5 validated or is blocked.
16. Retry known transient launch errors quietly up to 3 attempts before surfacing a failure.
17. Only mark the row blocked when the failure is persistent or non-transient.

## Permissions enforcement

The orchestrator reads `_agent-permissions.yaml` at startup. For each stage, it:

1. Looks up the stage entry to find the role (creator or auditor).
2. Gets the CLI command from the `agents` section for that role.
3. Appends tool restrictions:
   - Claude: adds `--allowedTools` flag with the tools from `allowed_tools`.
   - Codex: adds `--sandbox workspace-write`.
4. Injects the `allowed_read` and `allowed_write` paths into the prompt text.
5. Preloads the contents of explicit allowlisted text files before the agent starts.
6. Summarizes binary or very large external sources as path manifests instead of inlining them.
7. Replaces `{document}` in paths with the actual filename for the current row.

If a stage fails (non-zero exit, no JSON output, timeout, or known transient launch error):
1. Retry transient launch errors quietly up to 3 attempts with backoff.
2. Stop the pipeline loop only if the failure is persistent or non-transient.
3. Mark the document as blocked in `loop-state.json` with the error details when the failure is persistent.
4. Write a failure entry to `audit-log.jsonl` with stage, agent, error, and allowed permissions.
5. Exit. The `audit-pipeline-run` skill analyzes the log and explains the fix to the user.

## State files

- runbooks/index.md - document tracking grid (source of truth for stage progression)
- tools/audit/loop-state.json - per-document state (completed stages, quality trajectory, blocked status)
- tools/audit/audit-log.jsonl - append-only event log (one JSON line per stage invocation)

## Completion gate

A row is complete when S5 passes the post-run validator. The validator confirms that the runbook file, index.md, and _open-questions.md are consistent before the row is closed and the next row in index order is unlocked.

## Retroactive governance pass

After the meta-audit completes, if the retroactive pass is enabled:

1. Read the retroactive governance pass tracking section in the index.
2. Find the first row where S6 Verdict = `not-started`.
3. Launch auditor agent for S6 with the document + final governance files.
4. If S6 passes: mark S7/S8 as `skipped`, move to next row.
5. If S6 fails: launch creator agent for S7, then auditor agent for S8.
6. If S8 finds regressions: mark row blocked, stop processing that row.
7. Append S6/S7/S8 events to audit-log.jsonl.
8. When all rows are processed: write `Retroactive pass: done` in the index footer.
